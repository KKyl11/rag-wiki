RAG 是什麼？讓 AI 先查資料再回答

你問 AI 一個需要最新資訊的問題，它可能會編造答案——怎麼辦？

RAG（Retrieval-Augmented Generation，檢索增強生成）：讓語言模型先去資料庫找相關段落，再根據找到的內容寫答案。

📚 Wiki：concepts/rag.md · concepts/llm-knowledge-limits.md

問題

LLM 為什麼會答錯或過時？

只靠「背在參數裡的知識」回答的語言模型，有三個問題：

  • 幻覺（hallucination）：模型可能編造答案；遇到超出訓練資料、或需要最新資訊的問題時特別容易發生。
  • 過時：模型無法輕易擴充或修改記憶，要跟上世界變化得再訓練。
  • 無法追溯：模型難以說明答案的依據，說不出出處。
解法方向：引用外部知識，能有效減少事實錯誤的內容，也能持續更新知識。

概念

核心概念：背在腦中 vs 隨時翻課本

參數記憶（背在腦中）非參數記憶（可以翻的資料）
存在哪裡模型參數外部文件索引（例如 Wikipedia）
怎麼更新需要再訓練替換索引即可
看得懂嗎難以說明預測依據由原始文字構成，人可讀也可改

RAG 把兩者結合：模型本身的能力，加上一份可以翻的外部資料。

來源原有的比喻（Gao et al.）：RAG 像給模型一本量身訂做的課本隨時翻查；fine-tuning（微調）則像學生花時間把知識內化進腦中。

流程

RAG 怎麼運作：索引 → 檢索 → 生成

① 索引：把資料切成小塊，轉成向量存進資料庫
→
② 檢索：把問題也轉成向量，找出最像的 top-K 片段
→
③ 生成：問題＋片段一起交給 LLM 回答
  • 這是最基本的 RAG（Naive RAG），也叫「Retrieve-Read」流程：先檢索、再閱讀。
  • 原始論文的說法：檢索器取出 top-K 段文字，生成器根據問題與這些段落產生答案。
🎓 教學比喻（非來源內容）：像寫報告前先去圖書館——先替書做好目錄，再找出相關的幾頁，最後根據那幾頁寫答案。
📚 Wiki：concepts/rag-paradigms.md · concepts/rag.md

流程

第一步拆開看：切塊（chunking）

  • 為什麼要切？ 把長文件切成一小段一小段，檢索器才能一段一段比對、挑選。
  • 原始論文的做法：每篇 Wikipedia 文章切成不重疊的 100 字片段，共 21M 段。
  • 常見做法：以固定的 token 數切分，例如 100、256、512。
切大塊切小塊
好處保留較多脈絡雜訊少
代價雜訊多、處理時間與成本較高可能傳達不了必要的脈絡
📚 Wiki：concepts/chunking.md

流程

第二步拆開看：嵌入（embedding）與檢索

  • 嵌入（embedding）：把文件和問題各自編碼成向量，再計算相似度（例如 cosine similarity），找出最接近的 top-k 片段。
  • BM25：字詞重疊式的檢索，比對問題和片段裡相同的字詞。
  • 兩者互補：查「Error code TS-999」時，embedding 可能只找到一般錯誤碼的內容，BM25 則能精確比對「TS-999」。兩者捕捉不同的相關性特徵，可以混合（hybrid）互補。
🎓 教學比喻（非來源內容）：把每段文字想成地圖上的一個點，意思越像的文字靠得越近；檢索就是找出離「問題」最近的幾個點。
📚 Wiki：concepts/retriever.md

例子

具體例子：換掉外部索引，答案就跟著更新

RAG 原始論文的實驗：找出 82 位在 2016 到 2018 年間換人的世界領袖，問 RAG「Who is {position}?」（某個職位現在是誰？）

情況答對率
用 2016 的索引，問 2016 的領袖70%
用 2018 的索引，問 2018 的領袖68%
索引與年份對不上只剩 12% 與 4%
結論：只要替換非參數記憶（外部索引），就能更新 RAG 的世界知識，不需要重新訓練模型。

進階變形

進階 1：Contextual Retrieval——替片段補上下文

RAG 從最基本的 Naive RAG，演進到加入各種優化的 Advanced RAG 與 Modular RAG。以下是改良「檢索」的一個例子：

  • 問題：切塊後，片段「公司營收比上一季成長 3%」沒說是哪家公司、哪一季，很難被正確找到。
  • 做法：讓 Claude 讀整份文件與片段，生成 50–100 tokens 的說明加在片段前面，再建 embedding 與 BM25 索引。
  • 再加 reranking：初步檢索後重新排名，把最相關的片段排到前面。
做法（top-20 片段的檢索失敗率）失敗率
一般做法5.7%
＋ Contextual Embeddings3.7%（降 35%）
＋ Contextual BM252.9%（降 49%）
＋ Reranking1.9%（降 67%）

進階變形

進階 2：Self-RAG 與 GraphRAG

Self-RAG：需要時才查，查完自己檢查

  • 解決什麼：傳統 RAG 不管需不需要，都固定檢索一定數量的段落。
  • 做法：模型自己判斷要不要檢索，並用「反思標記」評估找到的段落是否相關、自己寫的內容有沒有被段落支持。

GraphRAG：回答「整份資料在講什麼」

  • 解決什麼：「資料集的主要主題是什麼？」這類全域問題，一般 RAG 會失敗。
  • 做法：先用 LLM 把文件建成知識圖、替每群相關內容寫摘要，回答時再彙整這些摘要。
  • 結果（兩個資料集的實驗）：在「全面性」上，GraphRAG 對一般 RAG 的勝率為 72–83%（Podcast）與 72–80%（新聞）；一般 RAG 的答案則最直接。
📚 Wiki：concepts/self-rag.md · concepts/graphrag.md

限制

RAG 也會答錯

最基本的 RAG（Naive RAG）可能在這兩個地方出錯：

  • 檢索：可能選到不相關的片段，或漏掉關鍵資訊。
  • 生成：可能產生檢索內容不支持的幻覺；整合多段資訊時也可能不連貫或重複。

RAG 原始論文也指出另一個限制：

  • 資料本身：Wikipedia 或任何外部知識來源，都不可能完全正確、完全沒有偏誤。
原始論文作者認為，以 Wikipedia 為依據能讓模型較少「幻覺」；但同一篇論文也承認，外部知識來源不可能完全正確。

限制與爭議

限制：資料塞越多越好嗎？（Lost in the Middle）

  • U 形曲線：關鍵資訊放在長輸入的開頭或結尾時，模型表現最好；放在中間時明顯變差。
  • 嚴重時：GPT-3.5-Turbo 在 20、30 篇文件設定的最差情況，比完全不給文件（closed-book，56.1%）還差。
  • 多放不一定有用：檢索器找到的相關文件越來越多，模型表現卻早就不再進步；超過 20 篇只帶來些微進步，卻大幅增加延遲與成本。
  • 對策：用 reranking 把相關資訊推到開頭，或少放幾篇。
⚖️ 兩種說法：Liu et al. 發現關鍵文件被淹在中間時，表現可能比不給文件還差；但 Gao et al. 引述的研究發現，加入不相關文件反而可能讓準確率提升超過 30%（與原本假設相反）。後者只有二手描述，無法比對兩者的實驗設定。
📚 Wiki：concepts/lost-in-the-middle.md · comparisons/rag-vs-long-context.md · sources/liu2023.md

限制與爭議

爭議：模型讀得下整本書，還需要 RAG 嗎？

現在的 LLM 能處理超過 200,000 tokens 的脈絡，引發「還需不需要 RAG」的討論。

可以不用 RAG 的時候

  • 知識庫小於 200,000 tokens（約 500 頁）時，可以直接把整個知識庫放進 prompt。

RAG 仍有價值的理由

  • 一次塞大量脈絡會明顯拖慢推理速度。
  • RAG 能找到原始出處讓人驗證；只靠長上下文的生成像黑盒子。
  • 讀得下不等於讀得好：擴充脈絡長度的模型也有中間迷失現象。
和 fine-tuning 的關係：兩者不互斥，可以互補。

回顧

重點回顧＋小測驗

  • RAG＝先去資料庫找相關段落，再根據找到的內容寫答案。
  • 流程：索引 → 檢索 → 生成。
  • 資料不是塞越多越好：放在中間的關鍵資訊容易被忽略。
  1. RAG 的三個步驟是什麼？索引、檢索、生成
  2. 想讓 RAG 知道新的事，一定要重新訓練模型嗎？不用，換掉索引就能更新知識
  3. 關鍵資訊放在長輸入的哪裡，模型最容易忽略？中間（Lost in the Middle）
  4. RAG 和 LLM Wiki 最大的差別是什麼？RAG 被問時才檢索；LLM Wiki 加入資料時就整理成 wiki
